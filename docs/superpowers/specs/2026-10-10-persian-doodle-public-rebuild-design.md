# PersianDoodle Public Rebuild Design

## Goal

Turn the existing source-first catalog into an honest, self-hosted Persian motion library. All source models and distinct variants remain searchable, while only verified project-owned Persian renders are playable as public output.

## Evidence from the current checkout

- `library/data/catalog.json` contains 534 entries: 306 Shotcraft, 15 MG Styles, 108 Talkcraft, 45 Explainer, 24 OneTake, and 36 native entries.
- `library/data/shotcraft-full.json` preserves 157 source cards and 214 distinct style executions.
- `library/data/source-audio.json` preserves 154 audio records: 5 music and 149 SFX.
- `library/media/` is absent and `library/data/persian-renders.json` has no published renders.
- The existing UI still loads source posters, source videos, and Mixkit audio when no local render exists.
- The engine already provides deterministic Canvas/Remotion rendering, Persian shaping, 25 declared font families, FFmpeg export, and browser QA tooling.

## Design

### Inventory and manifest

The source catalog remains the complete inventory. A generated render manifest becomes the only authority for public playback. Each source model has a status and each distinct variant has its own record. `identified` and `analyzed` entries remain searchable but have no player source; `rendered-persian` requires video, poster, thumbnail, prompt, and metadata files under `library/media/`.

The manifest generator will derive expected variant counts from the catalog and Shotcraft index, reject duplicate variant keys, and preserve source URLs only as attribution/research metadata. It will never infer a successful render from a filename or from a source URL.

### Native render pipeline

Native scenes live in `skills/anidoodle/engine/src/canvas-core/` and are selected by explicit technique families. A family is reusable implementation machinery, not a substitute for variant identity: each variant receives a stable seed, Persian copy, timing, palette, camera path, and technique-specific parameters derived from its analyzed source metadata. The initial families cover trace/write-on, kinetic typography, chart/counter, camera/transition, and collage/assemble. Each family exposes a deterministic Film and a still/contact-sheet renderer.

The batch renderer writes a variant directory containing `preview.mp4`, `poster.webp`, `thumb.webp`, `prompt.fa.md`, `meta.json`, and an editable scene/config file. It also emits a machine-readable render report with frame count, dimensions, codec, duration, and SHA-256.

### Audio

The 154 source audio records remain indexed with attribution and license metadata. Stock source URLs are never copied into a public player as project-owned audio. Published Persian scenes use either an explicitly licensed local asset or deterministic native sound generated by the engine. Audio manifests distinguish source reference, local preview, license state, and whether the asset is safe for publication.

### Browser contract

The library UI must resolve playable media only through the local render manifest. When a variant is not rendered, the detail panel shows its honest status and research links without assigning a foreign video URL to a `<video>` element. Local poster images may be shown only when they are listed in the manifest. The same rule applies to audio.

### Quality and release

Validation has four layers: manifest/path validation, media inspection with `ffprobe`, frame/contact-sheet inspection, and Playwright browser checks on desktop and mobile. GitHub Pages must fail if a published record points outside the repository, lacks a required file, has an invalid status, or leaves a source URL in a public media element.

## Delivery order

1. Establish the generated inventory/status manifest and make the current UI obey the local-only playback contract.
2. Add the native variant scene interface and render one representative, verifiable batch from each source family.
3. Add batch rendering, posters/thumbnails, Persian prompts, editable scene configs, and per-variant reports.
4. Render and verify the remaining distinct variants in queued batches; never mark failed or missing items as published.
5. Add local/native audio previews where licensing permits, update audio status records, and remove public source playback.
6. Run full CI, browser, mobile, media, and deployed-site verification before publishing.

## Explicit non-goals

- Replacing a distinct source motion with a color-only or title-only clone.
- Publishing a source video under a Persian title.
- Treating a successful render command as proof that a media file is valid or faithful.
- Deleting source inventory records to make completion counts smaller.
